# 2026-11-09 저장소 복구 안내 재발 조사

## 확인 범위

2026-11-07 및 11-09 긴급 복구에서 readiness 503, 로컬 Redis PONG, `draft:v1:writer` PTTL -2(키 없음)를 확인했다. 유효한 방이 없는 상태에서 밴픽 서비스만 재시작하자 ready 200과 잠금 갱신이 복원되었다. 이번 조사는 재시작 이후 운영 자료를 수정하지 않는 조회와 별도 임시 Redis의 장애 재현만 수행했다.

운영 밴픽 실행 코드는 `91d786313399dad137b16efba21ad91c7388e05a`다. 게이트웨이는 서버에 실제 설치된 `/opt/owkr-storage/storage-sync.py`와 `storage-backup.py`를 직접 읽어 확인했다. 운영 동기화는 매일 한국 시각 03:00 예약 방식으로, 현재 작업 디렉터리의 동기화 코드와 차이가 있으므로 수정 시 운영 버전과 대조해야 한다.

## 확정한 장애 지속 원인

- 쓰기 잠금은 시작 시 NX/PX 15초로 획득하고 5초마다 기존 소유자 값이 같은 경우에만 PEXPIRE한다.
- 키가 만료되면 renewLease는 0을 반환한다. 상태 관리 루프는 갱신 성공을 먼저 요구하므로 recover에 진입할 수 없다. 키가 없는 상태가 계속되어도 잠금 재획득이나 프로세스 종료 경로가 없다.
- 프로세스는 healthy=false 상태로 계속 살아 있다. systemd는 Restart=on-failure, WatchdogUSec=0이므로 readiness 503만으로는 재시작하지 않는다. 따라서 일시적인 잠금 소실이 수동 재시작 전까지 지속되는 장애로 바뀐다.

## 재현한 잠금 소실 경로

운영 게이트웨이 StorageSync.execute는 잠금 키가 동기화 대상에서 제외되더라도 먼저 공용 self.lock을 잡는다. reconcile은 같은 잠금을 잡은 채 외부 Upstash 요청과 SQLite 작업을 수행하며, 백업 capture도 같은 잠금을 쓴다. 그 사이 잠금 갱신 REST 요청이 대기할 수 있다. 관리 작업 대기열과 독립된 Node 갱신 타이머를 두어도 게이트웨이의 공용 잠금에서 다시 막힌다.

서버에 설치된 실제 동기화 모듈과 별도 임시 Unix socket Redis·SQLite를 사용했다. 외부 요청은 이벤트로 16초 지연시킨 모의 응답이다. 운영 Redis·Upstash에는 연결하지 않았다. 동일한 15초 writer 키를 만들고 reconcile이 공용 잠금을 가진 동안 동일한 갱신 Lua를 execute에 전달했다.

결과:

```json
{"isolated":true,"redisResponsive":true,"leaseRenewalQueueMs":16006,"renewalResult":0,"writerTtlMs":-2,"syncErrors":[]}
```

이는 공용 잠금 지연이 writer 만료를 유발할 수 있다는 재현이다. 이번 운영 장애에서 실제로 어떤 외부 요청·백업·호스트 지연이 15초를 넘겼는지 입증한 기록은 아니다. 운영 로그에는 잠금 상실 시각·요청 대기 시간·원인 분류가 없다. 외부 통신의 timeout=0.7초 설정만으로 전체 공용 잠금 보유 시간을 0.7초 이하라고 보장할 수 없다.

## 추가 확인

- Redis evicted_keys=0, noeviction, 사용 메모리 약 1.54MiB. 메모리 초과에 따른 강제 키 축출의 증거는 없다.
- writer는 managed_key에서 제외되며 실제 동기화 states 테이블에도 해당 키가 0건이었다. 원격 병합이 writer 키를 직접 덮어썼다는 증거는 없다.
- 조사 범위의 커널 기록에서 OOM·stall·clock jump 관련 메시지를 발견하지 못했다. 같은 부팅이 계속 유지되었다. 호스트 일시 정지나 순간 스케줄링 지연까지 배제한 것은 아니다.
- 최근 Redis slowlog 표본은 수십 ms 수준으로, 확인한 표본에서 15초짜리 Redis 명령은 발견하지 못했다. 표본/보존 범위 밖의 지연까지 배제할 수는 없다.
- 조사 종료 시 공개 readiness는 ready/redis였다. 운영 설정·코드를 변경하지 않았다.

## 근본 수정 방향

1. writer 전용 명령은 동기화/백업의 공용 잠금과 SQLite 경로를 통과하지 않도록 별도 처리한다. 일반 데이터 및 혼합 키 명령의 원자성과 저널 보장은 그대로 유지한다.
2. 확정적인 lease 소실 시 입력을 차단하고 안전하게 종료·재시작하거나, 작성자 충돌 방지와 방 복구 절차를 포함한 재획득을 구현한다. 다른 프로세스의 잠금을 강제로 가져오면 안 된다.
3. lease 상실·마지막 성공 후 경과·갱신 요청 지연·게이트웨이 공용 잠금 대기를 비밀값 없이 기록한다. readiness 지속 실패 감시를 보완한다.
4. 외부 요청/백업 지연 중에도 갱신 유지, lease 소실 후 안전 복구, 다른 작성자 잠금 보존, 실제 방 상태/봉인 결과 보존을 격리 테스트한다. TTL만 늘리는 조치로 끝내지 않는다.

코드 수정과 재배포는 이번 원인 조사에 포함하지 않았다. 기존 작업 중인 storage-sync-test.py 변경은 수정하거나 덮어쓰지 않았다.


## 2026-11-13 근본 수정

최신 운영 커밋 91d7863 기준으로 수정했다. 알려진 단일 writer 키의 SET/GET/TTL 및 소유자 확인 갱신·해제 Lua만 동기화/SQLite 공용 잠금을 우회한다. 임의 Lua·혼합 데이터 명령은 기존 경로를 유지한다. 일반 요청 16개가 동기화 잠금을 기다릴 때도 갱신 요청이 진입하도록 HTTP 동시성 2개를 별도로 예약했다. writer 작업 자체가 1초 이상 걸리면 비밀값 없이 지연을 기록한다.

독립 lease 감독기는 갱신을 중복 실행하지 않고 5초 주기로 유지한다. 소유권 상실이 확정되거나 갱신 성공 없이 15초가 지나면 새 입력을 차단하고 연결을 끊은 뒤 운영 프로세스가 실패 종료한다. 기존 systemd Restart=on-failure가 새 프로세스를 시작하며, 새 임의 작성자 ID로 NX 잠금을 획득한 뒤 기존 방 복구 절차를 실행한다. 다른 소유자 잠금을 삭제하거나 가져오지 않는다. 잠금 상실 사유와 마지막 성공 이후 경과 시간을 로그에 남긴다. 일시적인 통신 오류가 만료 전 해소되면 재시작하지 않는다.

회귀 검증은 16초 지연된 외부 동기화 중 실제 15초 잠금 유지, 일반 HTTP 16개 포화 시 갱신 통과, 다른 작성자/누락 잠금의 갱신·해제 거절, 혼합 데이터 명령 저널 유지, 15초 이상 응답하지 않는 갱신 감독, 만료 뒤 늦게 온 성공 응답 무시, 서버 입력 차단을 포함한다. 기존 백업/동기화/삭제/TTL/트랜잭션 검사를 함께 실행한다. 최초 운영 장애의 지연 작업이 미확정이라는 조사 결론은 유지한다.

검증 결과: pnpm check 101파일/599테스트 및 타입·린트·경계·프런트/서버 빌드 통과. 실제 Linux Redis 2개를 격리 실행한 통합 검사 36개 통과. 패키징한 운영 진입점을 별도 내부 포트에서 16초 SIGSTOP 후 재개하자 renewal-timeout/elapsedMs 로그와 exit 1을 확인했고, 교체 프로세스의 ready 200을 확인했다. 운영 서비스나 실제 Redis 자료에는 장애를 주입하지 않았다.
