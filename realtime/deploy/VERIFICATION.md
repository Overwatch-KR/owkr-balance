## 발견 및 수정

처음에는 동시 접속마다 사용자 수에 비례해 Redis를 반복 조회했다. 직렬 대기 중 인증 5초 제한이 발생했으며 writer lease 갱신도 대기열 뒤로 밀릴 수 있었다. 방송마다 방을 한 번 읽고 사용자별 권한을 적용하며, 유효한 입장권 수신 시점에 인증 타이머를 해제하고 lease는 별도 주기로 갱신하도록 수정했다.

추가 시험 중 배포자가 Caddy를 reload해 기존 연결이 끊겼다. WebSocket 종료 지연 5분을 설정했다. 다시 reload하면서 HTTP keep-alive 소켓이 닫혀 시험의 단일 health fetch가 실패한 기록도 있다. 최종 정상 부하 시험은 설정 변경 없이 다시 실행했다. 이 실패를 지속 부하 시험 통과로 계산하지 않는다.

## 최초 인수인계 시점의 상태와 남은 작업

TLS 프록시·배포 파일 설치와 격리 서버 시험을 완료해도 전체 서비스 공개 완료를 뜻하지 않는다. 시험 종료 뒤 임시 프로세스와 시험 키를 정리하고, OAuth 정보가 없는 실제 운영 프로세스는 시작하지 않는다. 따라서 현재 `/health/ready`는 503이다.

1. 참가자 전용 Discord 앱 Client ID / Secret을 `/etc/owkr-draft/participant-oauth.env`에 등록하고 Redirect URI를 설정한다.
2. 현재 서버 Origin `https://owkr-internal-balance.vercel.app`이 실제 사이트 주소와 같은지 확정한다.
3. Vercel 담당자가 전달받은 RSA 개인키/bridge secret/API 주소를 Production에 등록하고 재배포한다.
4. 실제 관리자 방 생성, 실제 명단 Discord 로그인·세션 복구·재접속을 검증한다. 그 후 기능 플래그를 활성화한다.
5. 기존 미완료 P0, 실제 게임 적용, 모바일/쿠키 차단, 10방/240소켓 및 장시간 부하는 별도 검증이 남는다. 이 측정만으로 기존 Java 서비스의 최대 메모리 사용과 겹치는 상황까지 보장하지 않는다.

SSH 키와 전달용 비밀 파일은 Git에서 제외했다. 운영 절차는 [OPERATIONS.md](OPERATIONS.md)를 참고한다.
